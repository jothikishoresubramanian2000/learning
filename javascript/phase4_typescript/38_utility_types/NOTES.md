# Module 38 — Utility Types

### What I learned today

Up to this module, every time I wanted a "variant" of an existing shape — say, the same
`Product` but with every field optional, or the same `Employee` but without the sensitive
`ssn` field — the only tool I had was to write a whole new interface by hand, duplicating
most of the original's fields. This module introduces TypeScript's **utility types**:
built-in generic type TRANSFORMATIONS that take an existing type and produce a new,
derived one, without retyping anything. `Partial<T>`, `Pick<T, K>`, `Omit<T, K>`,
`Record<K, V>` (already met briefly in Module 36), and `Readonly<T>` are the ones covered
here. The single biggest thing to watch for: `Partial<T>` makes every field optional, which
is exactly right for an "update" shape, but can be DANGEROUSLY dishonest if misused for
something that's supposed to be complete.

### File: `util_task1.ts` — line by line

```ts
interface Product{
    id: string,
    name: string,
    price: number,
    secret: string
}

type OptionalData=Partial<Product>
type PickData = Pick<Product,"id"|"name">
type OmitData = Omit<Product, "secret">
```
Three different transformations of the SAME base interface:
- `Partial<Product>` — takes every one of `Product`'s properties and makes them ALL
  optional (`id?`, `name?`, `price?`, `secret?`). Still has all four properties, just none
  of them required anymore.
- `Pick<Product, "id"|"name">` — the opposite kind of operation: keeps ONLY the named
  properties (`id` and `name` here, listed as a literal union of the keys to keep) and
  drops everything else. The result type has exactly two fields.
- `Omit<Product, "secret">` — the inverse of `Pick`: keeps EVERYTHING except the named
  property. The result has `id`, `name`, `price` — everything but `secret`.

```ts
const updateUser: Partial<OptionalData> = {id:"P-002",name:"berowvu",price:1000,secret:"key"}
```
`Partial<OptionalData>` is `Partial<Partial<Product>>` — wrapping `Partial` around an
already-`Partial` type. This is harmless but redundant: once every field is already
optional, making them "optional again" changes nothing. The object here actually
supplies ALL four fields anyway, which is also allowed, since `Partial` only makes fields
NOT required — it never forbids supplying them.

```ts
const myId: PickData = {id:"P-001",name:"Pena"}
const safe: OmitData ={id:"P-003",name:"Kunda",price:100}
```
`myId` can only have `id` and `name` (that's all `PickData` kept). `safe` has `id`,
`name`, `price` — everything `Product` had except `secret`, matching what `OmitData`
produced.

### File: `util_task2.ts` — line by line

```ts
type Inventory = Record<"pen"|"book"|"bag",number>

const myInventory: Inventory ={
    pen: 10,
    book: 20,
    bag: 5
    //laptop: 10 - Object literal may only specify known properties, and 'laptop' does not exist in type 'Inventory'.
}
console.log(myInventory.pen) 
```
`Record<K, V>` again, same pattern as Module 36's `ScoreCard` — a closed set of exactly
three keys (`"pen" | "book" | "bag"`), each mapping to a `number`. Adding a fourth key
like `laptop` is rejected because it isn't part of the `K` union — this is ALSO an excess
property check (Module 33) in action, since `myInventory` is an inline object literal
being checked directly against `Inventory`.

```ts
interface Font{
    theme: string,
    fontSize: number
}
type RSerttings = Readonly<Font>

const myFont: RSerttings = {theme: "Winter", fontSize: 100}

//myFont.fontSize = 90 - Cannot assign to 'fontSize' because it is a read-only property.
console.log(myFont) 
```
`Readonly<Font>` takes EVERY property of `Font` and marks it `readonly` (same effect as
writing `readonly` by hand in front of each property, but applied automatically to all of
them in one step — and also similar in spirit to `as const`'s readonly effect from Module
32b, except `Readonly<T>` is a TYPE-level transformation applied at the declaration,
while `as const` is applied to a specific VALUE). Trying `myFont.fontSize = 90` afterward
triggers the same "read-only property" error seen with `readonly id` back in Module 33
and `as const`'s `config.retry` back in Module 32b — three different ways to arrive at
the identical protection.

### File: `util_task3.ts` — line by line

```ts
interface Employee { id: string; name: string; salary: number; ssn: string }

type CreateEmployee = Omit<Employee,"id">
type UpdateEmployee = Partial<Omit<Employee,"id">>
type PublicEmployee = Omit<Employee,"ssn">
```
Three DIFFERENT, purpose-built variants of one base interface, each modeling a real,
distinct use case in a typical backend:
- `CreateEmployee` — everything needed to CREATE a new employee, minus `id` (since an id
  is usually generated by the system, not supplied by the caller). Still fully required
  otherwise.
- `UpdateEmployee` — `Omit<Employee, "id">` (no `id`, same as above) WRAPPED in
  `Partial<...>` — composing two utility types together. This produces "any subset of
  `name`/`salary`/`ssn`, all optional" — exactly right for a partial update where the
  caller only sends the fields they want to change.
- `PublicEmployee` — everything except the sensitive `ssn` field, meant for a version of
  the employee data that's safe to expose publicly (API responses, logs, etc.) without the
  sensitive field even existing on the type.

```ts
const emp1 : CreateEmployee = {name: "kishore",salary: 10,ssn:"hi"}
const updateEmp: UpdateEmployee = {name: "SK",salary: 10,ssn:"hi"}
//const updateEmp: UpdateEmployee = emp1 - this make silent entry?
const gEmp: PublicEmployee = {id: "EMP-003",name:"Jk",salary: 20}
```
`emp1` provides all three non-id fields — valid for `CreateEmployee`, which still requires
all of them. `updateEmp` ALSO provides all three here, which is also valid, since
`Partial` only makes fields optional, never forbidden — a fully-filled-in object still
satisfies a `Partial` type.

My own commented-out line, `const updateEmp: UpdateEmployee = emp1`, asks a sharp
question — "this make silent entry?" The answer: yes, and it's worth being precise about
why it's "silent." `emp1` (a `CreateEmployee`) has `name`, `salary`, `ssn` — ALL of which
also happen to be valid, optional fields on `UpdateEmployee`. So assigning `emp1` to an
`UpdateEmployee`-typed variable compiles without complaint — not because TypeScript is
confused, but because `CreateEmployee`'s full shape genuinely IS a valid (if fully
populated) `UpdateEmployee`. Nothing is silently lost or mismatched here; it's just a
case where "more complete than required" is still accepted, the same as `Partial`
accepting a fully-filled object back in `util_task1.ts`.

```ts
// Object literal may only specify known properties, and 'dept' does not exist in type 'PublicEmployee'. this is the error when I try to add new feild
```
Confirms, yet again, excess property checking on an inline literal — adding a field
that's not part of the target type (here, `dept` isn't part of `Employee` at all, so
certainly not part of `PublicEmployee`) is caught immediately.

```ts
// if not utilities, there would be redundant interfaces
// example - interface CreateEmployee {name: string; salary: number; ssn: string }
//again for update. same, just optional, but we need to write again
//interface UpdateEmployeesss {name?: string; salary?: number; ssn?: string }
```
This final comment is the real takeaway of the module, in my own words: without utility
types, I'd be hand-writing near-duplicate interfaces every time I needed a variant of an
existing shape — and every time the base `Employee` interface changed (say, adding a
`department` field), I'd have to remember to update EVERY hand-written duplicate too.
`Omit`/`Pick`/`Partial` derive from the ORIGINAL interface, so a change to `Employee`
automatically flows through to `CreateEmployee`, `UpdateEmployee`, and `PublicEmployee`
without touching them at all.

### Gotchas worth remembering from this module

- **`Partial<T>` can be dangerously dishonest if used for the wrong purpose.** It's
  exactly right for "a genuine partial update" (`UpdateEmployee`), but using it to
  describe data that's SUPPOSED to be complete (e.g., asserting untrusted JSON input as
  `Partial<T>` and then forgetting the verification step — the exact trap Module 32b
  warned about) means TypeScript will happily let required-looking fields be missing
  without complaint. `Partial` is a legitimate, useful type when "maybe missing" is the
  TRUTH; it becomes a loophole the moment it's used to paper over data that should have
  been fully validated instead.
- **Composing utility types (`Partial<Omit<Employee, "id">>`) applies them inside-out** —
  `Omit<Employee, "id">` runs first, producing a smaller shape, and THEN `Partial` is
  applied to that already-narrowed result, not to the original `Employee`. Reading the
  composition from the innermost type outward is the right mental model.
- **A fully-populated object still satisfies a `Partial` type** — `Partial` only removes
  the REQUIREMENT, it never forbids providing more. This is why `emp1` (fully filled)
  type-checks fine as an `UpdateEmployee` even though `UpdateEmployee` only technically
  requires zero of its fields to be present.
- **Utility types stay LINKED to their source interface — plain hand-duplicated
  interfaces don't.** The entire point of reaching for `Omit`/`Pick`/`Partial` instead of
  writing `CreateEmployee`/`UpdateEmployee` as independent interfaces from scratch is that
  a later change to `Employee` propagates automatically; independently hand-written
  duplicates would silently drift out of sync with the original the next time someone
  updates `Employee` without remembering to also update every copy.
